# สเปกการรับและนำเข้าข้อมูลเกียรติบัตร (Data Intake & Processing Spec)

เอกสารนี้สรุปข้อกำหนด รูปแบบโครงสร้างไฟล์ต้นฉบับ และกระบวนการนำเข้าข้อมูล (Data Intake Workflow) ก่อนนำเข้าสู่ระบบ OCEC-Cert

---

## 1. ภาพรวมรอบการสอบและรูปแบบไฟล์ต้นฉบับ (Raw Data Overview)

การสอบจัดขึ้นเป็น 2 รอบหลัก โดยมีลักษณะไฟล์เกียรติบัตรที่ได้รับมาดังนี้:

| รอบการสอบ | กลุ่มผู้สอบในไฟล์ PDF | การแบ่งไฟล์ตามรางวัล (Award) | เงื่อนไขการคัดกรองประเทศ |
|---|---|---|---|
| **1. รอบ Heat (รอบคัดเลือก)** | เฉพาะของไทย (Domestic) | รวมเล่ม PDF แยกตามโฟลเดอร์เหรียญรางวัล | ตัดแยกทุกหน้า ไม่ต้องกรองสัญชาติ |
| **2. รอบ Final (รอบชิงชนะเลิศ)** | รวมทุกประเทศ (International) | รวมเล่ม PDF แยกตามโฟลเดอร์เหรียญรางวัล | **ต้องสแกนคัดเฉพาะคนไทย** (`from THAILAND`) ข้ามชาติอื่น |

### ประเภทรางวัล/เหรียญรางวัล (Awards)
ไฟล์ PDF รวมเล่มจะถูกจัดกลุ่มมาในโฟลเดอร์ 5 รางวัล ได้แก่:
1. `gold` (เหรียญทอง)
2. `silver` (เหรียญเงิน)
3. `bronze` (เหรียญทองแดง)
4. `merit` (รางวัลชมเชย)
5. `perfect score` (คะแนนเต็ม)

## 2. โครงสร้างไฟล์ Excel รายชื่อ (Roster Sheet)

ไฟล์สรุปรายชื่อผู้เข้าสอบจากส่วนกลางจะมีหัวตาราง (Columns) ดังนี้:

| หัวคอลัมน์ (Excel) | ข้อมูล | ตัวอย่าง | นำไปใช้ในระบบอย่างไร |
|---|---|---|---|
| `CANDIDATE NO` | รหัสประจำตัวผู้สอบ | `HK2024-0012` | บันทึกเข้าฐานข้อมูล (ช่วยระบุตัวตน / อ้างอิง) |
| `GRADE` | ระดับชั้น | `Primary 5`, `G.6` | บันทึกลงระดับชั้นของผู้เข้าสอบ |
| `CANDIDATE NAME` | ชื่อ-นามสกุล (อังกฤษ) | `SOMCHAI JAIDEE` | ใช้ Normalize เพื่อจับคู่กับชื่อบนเกียรติบัตร |
| `AWARD` | รางวัลที่ได้รับ | `Gold`, `Silver` | ใช้เป็นเงื่อนไขร่วมในการจับคู่ |

> **⚠️ ข้อเท็จจริงสำคัญมาก (Critical Fact) — แก้ไขหลังตรวจไฟล์จริงแล้ว**
>
> ~~บนหน้าเกียรติบัตร PDF ไม่มี `CANDIDATE NO` ระบุอยู่~~
>
> **ข้อเท็จจริงที่ตรวจพบ:** หน้าเกียรติบัตร **มี** บรรทัด `Cert No: 203297` อยู่ทุกหน้า
> และเลขนั้น **คือเลขเดียวกันกับ `CANDIDATE NO` ใน Excel**
>
> ตรวจกับชุด HKIMO Final 2026 (242 หน้า / 240 แถว) แล้วตรงกัน **242/242 หน้า ทั้งเลขและชื่อ**
> ระบบจึงจับคู่ด้วยเลขเป็นหลัก แล้วใช้ชื่อยืนยันอีกชั้น (เลขตรงแต่ชื่อไม่ตรง = ส่งให้แอดมินดู)
>
> **และรางวัลไม่ควรเป็นคีย์จับคู่** เพราะ Excel บันทึกรางวัลสูงสุดของคนนั้นแค่แถวเดียว
> ผู้ที่ได้ `PERFECT SCORER` มีเกียรติบัตร 2 ใบ (Gold + Perfect Score) แต่มีแถวเดียวใน Excel
> ถ้าใช้ `ชื่อ + รางวัล` เป็นคีย์ หน้า Gold ของคนเหล่านี้จะจับคู่ไม่ได้ทันที

## 3. โครงสร้างแพ็กเกจไฟล์ที่แอดมินอัปโหลด (ZIP Intake Structure)

เพื่อให้ระบบรู้รางวัลของแต่ละไฟล์ PDF โดยอัตโนมัติ แอดมินจะจัดโครงสร้างไฟล์และบีบอัดเป็น `.zip` อัปโหลดเข้าระบบ:

```text
📦 HKIMO_Heat_2024.zip (หรือ HKIMO_Final_2024.zip)
 ├── 📁 gold/
 │    └── *.pdf          (ไฟล์ PDF รวมเล่มของเหรียญทอง)
 ├── 📁 silver/
 │    └── *.pdf          (ไฟล์ PDF รวมเล่มของเหรียญเงิน)
 ├── 📁 bronze/
 │    └── *.pdf          (ไฟล์ PDF รวมเล่มของเหรียญทองแดง)
 ├── 📁 merit/
 │    └── *.pdf          (ไฟล์ PDF รวมเล่มของรางวัลชมเชย)
 └── 📁 perfect score/
      └── *.pdf          (ไฟล์ PDF รวมเล่มของ Perfect Score)
```

* หมายเหตุ: ชื่อโฟลเดอร์ใน zip จะถูก normalize ให้เป็นค่าคงที่ของระบบ (เช่น `gold`, `silver`, `bronze`, `merit`, `perfect_score`)

## 4. รูปแบบการตั้งชื่อไฟล์หลังการตัดแยก (PDF Renaming Format)

ระบบจะทำการตัดแยก (Split) PDF รวมเล่มออกมาเป็นไฟล์เดี่ยว 1 หน้าต่อ 1 คน และเปลี่ยนชื่อไฟล์ให้อัตโนมัติ:

### รูปแบบชื่อไฟล์:
```text
{fname}_{lname}_{รายการสอบ}_{award}_{ปีที่สอบ}.pdf
```

### องค์ประกอบในชื่อไฟล์:
1. **`fname_lname`**: ชื่อและนามสกุลภาษาอังกฤษที่สกัดได้จากข้อความในหน้าเกียรติบัตร (แปลงเป็นตัวพิมพ์ใหญ่ และแทนช่องว่างด้วย `_`)
2. **`รายการสอบ`**: รหัสรายการสอบและรอบ เช่น `HKIMO_HEAT` หรือ `HKIMO_FINAL`
3. **`award`**: รางวัลที่ได้ ซึ่งได้มาจากชื่อโฟลเดอร์ย่อยใน zip (`GOLD`, `SILVER`, `BRONZE`, `MERIT`, `PERFECT_SCORE`)
4. **`ปีที่สอบ`**: ปี ค.ศ. ที่สกัดได้จากข้อความบนเกียรติบัตร เช่น `2024`

### ตัวอย่าง:
* `SOMCHAI_JAIDEE_HKIMO_HEAT_GOLD_2024.pdf`
* `PIYADA_SRISUK_HKIMO_FINAL_PERFECT_SCORE_2024.pdf`

## 5. ขั้นตอนการประมวลผลและการจับคู่ (Processing & Matching Workflow)

```
[ แอดมิน ]
   │
   ├─ 1. อัปโหลด ZIP เกียรติบัตร (แยกโฟลเดอร์ตามเหรียญ)
   │     │
   │     ▼
   │  [ Worker: Unzip & Split ]
   │     ├─ อ่าน Award จากชื่อโฟลเดอร์ (gold, silver, ...)
   │     ├─ สแกนข้อความในหน้า:
   │     │   ├─ รอบ Final: ตรวจ 'from THAILAND' (ถ้าไม่ใช่คนไทย -> ข้ามทันที)
   │     │   └─ รอบ Heat: ประมวลผลทุกหน้า
   │     ├─ ดึง ชื่อ (Name) + ปีการศึกษา (Year ค.ศ.)
   │     ├─ Rename & Split PDF รายคน + Render รูป Preview WebP
   │     └─ บันทึกลง staging_pages (เก็บชื่อ, award, level, raw text, file keys)
   │
   ├─ 2. อัปโหลด Excel รายชื่อ (CANDIDATE NO, GRADE, CANDIDATE NAME, AWARD)
   │     │
   │     ▼
   │  [ Worker: Match Excel ]
   │     ├─ อ่านแถวใน Excel: Normalize ชื่อ และ Normalize รางวัล
   │     ├─ จับคู่กับ staging_pages โดยใช้:
   │     │   1) Name ตรงกัน
   │     │   2) Award ตรงกัน
   │     └─ [ กฎกรณีชื่อซ้ำ ]:
   │         ├─ ถ้าชื่อเดียวกัน แต่ได้ "คนละรางวัล" -> บันทึกและเก็บทั้งสองรางวัล
   │         └─ ถ้าชื่อเดียวกัน และ "รางวัลเดียวกัน" ซ้ำซ้อน -> ส่งเข้า AMBIGUOUS ให้แอดมินตรวจ
   │
   └─ 3. แอดมินตรวจสรุป และกดเผยแพร่ (Publish) -> ผู้ปกครองค้นหาและดาวน์โหลดได้
```

## 6. กฎการจับคู่และการจัดการกรณีชื่อซ้ำ (Matching & Duplication Rules)

1. **คีย์หลักในการจับคู่ (Match Key):** — ปรับตามข้อเท็จจริงที่ตรวจพบ
   * **หลัก:** `Cert No` บนหน้าเกียรติบัตร = `CANDIDATE NO` ใน Excel แล้วเทียบชื่อยืนยัน
   * **สำรอง:** ถ้าหน้าไหนอ่านเลขไม่ได้ ใช้ `normalized(CANDIDATE NAME)` โดยต้องตรงกับแถวเดียวเท่านั้น
   * **รางวัลไม่ใช่คีย์** — รางวัลของใบที่ออกมาจากชื่อโฟลเดอร์ใน ZIP เสมอ
     ส่วนคอลัมน์ `AWARD` ใน Excel ใช้เป็นแค่ตัวตรวจทาน
2. **กรณีผู้เข้าสอบชื่อเดียวกัน (Duplicate Student Names):**
   * **คนละรางวัล:** หากเด็ก 1 คนลงแข่งหลายประเภทหรือได้รับมากกว่า 1 รางวัล (เช่น ได้ทั้ง Gold ในหมวดหนึ่ง และ Perfect Score หรือได้ Merit เพิ่ม) -> **เก็บทั้งสองใบ** โดยสร้าง `Certificate` แยกรายการรางวัลให้ผู้เข้าสอบคนนั้น
   * **รางวัลเดียวกัน ซ้ำซ้อน:** หากชื่อเดียวกันและรางวัลเดียวกันโผล่ซ้ำในรอบเดียวกัน -> ถือเป็น `DUPLICATE_NAME` หรือ `AMBIGUOUS` ให้แอดมินเปิดดูหน้าจริงเพื่อยืนยัน (เช่น เป็นคนละคนที่มีชื่อพ้องกัน หรือเป็นไฟล์ที่เผลอใส่ซ้ำมา)

## 7. สิ่งที่ต้องปรับปรุงในระบบปัจจุบัน (System Adjustments Needed)

เพื่อให้รองรับสเปกใหม่ตามที่อธิบาย ระบบจะต้องปรับปรุงดังนี้:

1. **การอัปโหลดไฟล์ (Upload Component & Storage):**
   * เปลี่ยนจากการรับไฟล์ PDF รวมเล่ม 1 ไฟล์ เป็นการรับไฟล์ `.zip`
   * Worker ต้องเพิ่มความสามารถในการ Unzip และสำรวจโครงสร้าง Directory ภายใน
2. **การผูก Award ในขั้นตอน Split:**
   * บันทึกค่า `award` ลงใน `staging_pages` ตั้งแต่ขั้นตอน Split โดยอ่านจากชื่อ Folder ใน ZIP
   * สกัดปี ค.ศ. จากข้อความบนเกียรติบัตร เพื่อนำมาประกอบชื่อไฟล์
3. **การปรับปรุงฐานข้อมูล (Prisma Schema):**
   * เดิมที `Certificate` มีเงื่อนไข `@@unique([examId, studentId])` ซึ่งห้ามเด็ก 1 คนมีมากกว่า 1 ใบในรอบการสอบเดียวกัน
   * **ต้องปรับเป็น:** อนุญาตให้มีหลายใบได้หากเป็นคนละรางวัล หรือกำหนด unique ร่วมกับ `award` เช่น `@@unique([examId, studentId, award])` หรือใช้ `stagingPageId`
   * เพิ่มฟิลด์ `candidateNo` ลงในตาราง `Student` หรือ `Certificate`
4. **ตรรกะการ Match ใน Worker (`match_excel.py`):**
   * วนจาก "หน้าที่ตัดได้" ไม่ใช่ "แถวใน Excel" เพราะ 1 แถวรองรับได้หลายหน้า
   * จับด้วย `Cert No` ก่อน แล้วเทียบชื่อยืนยัน

## 7.1 การเติมไฟล์ที่ตกหล่น (Incremental Intake)

ของจริงต้นทางมักส่งเกียรติบัตรมาไม่ครบ แล้วส่งตามมาทีหลัง ระบบจึงรองรับการ **เติม**
ไฟล์เข้ารอบนำเข้าเดิม โดยไม่แตะของที่นำเข้าไปแล้ว

| โหมด | ใช้เมื่อ | ผลกับข้อมูลเดิม |
|---|---|---|
| `append` | ได้ไฟล์ที่ตกหล่นมาเพิ่ม | ไม่แตะเลย เติมเฉพาะใบที่ยังไม่มี |
| `replace` | ไฟล์ชุดเดิมผิดทั้งชุด | ลบหน้าทั้งหมดของรอบนั้นทิ้งแล้วตัดใหม่ |

**คีย์ที่ใช้ตรวจว่าซ้ำ: `เลขผู้เข้าสอบ + รางวัล`**

ต้องมีรางวัลประกอบเสมอ เพราะคนเดียวได้หลายใบคนละรางวัลเป็นเรื่องปกติ
ของจริงเคยเจอว่าต้นทางส่งใบ Perfect Score มาให้ แต่ใบ Gold ของคนเดียวกันหายไป
ถ้าตรวจซ้ำด้วยเลขอย่างเดียว ใบ Gold ที่ตามมาทีหลังจะถูกมองว่าซ้ำแล้วโดนทิ้ง

ถ้าหน้าไหนอ่านเลขไม่ได้ จะใช้ชื่อที่ normalize แล้วแทน
ถ้าอ่านไม่ได้ทั้งเลขและชื่อ จะเติมเข้าไปเลย (บอกไม่ได้ว่าซ้ำหรือไม่ — ดีกว่าเผลอทิ้งใบที่ควรมี)

### เติมทีละใบ (ไฟล์ตกหล่นไม่กี่คน)

ระบบรู้อยู่แล้วว่าใครขาดอะไร จึงแสดงเป็นบล็อกรายคนให้โยน PDF เข้าไปตรง ๆ
ไม่ต้องสร้างโฟลเดอร์ ไม่ต้องอัด ZIP ไม่ต้องเลือกรางวัล

| ที่มาของรายการ | ระบบรู้อะไร |
|---|---|
| มีชื่อใน Excel แต่ไม่มีหน้าเกียรติบัตร | ชื่อ, เลขผู้เข้าสอบ, รางวัล (จาก Excel) |
| มีใบ Perfect Score แต่ไม่มีใบเหรียญ | ชื่อ, เลขผู้เข้าสอบ, และรู้ว่าใบที่ขาดคือเหรียญทอง |

**ตรวจก่อนรับ:** เทียบเลขผู้เข้าสอบบนหน้ากับคนในบล็อกนั้น ถ้าไม่ตรงจะปฏิเสธ
พร้อมบอกว่าไฟล์นั้นเป็นของใคร และไม่แตะข้อมูลเดิมเลย
รางวัลอ่านจากข้อความบนหน้าก่อน (หน้า Perfect Score ไม่มีให้อ่าน จึงใช้ค่าที่ระบบคาดไว้)

เบื้องหลังใช้ทางเดินเดียวกับการอัป ZIP ทุกอย่าง โดยห่อ PDF เป็น ZIP โฟลเดอร์เดียวก่อน
จึงได้ตรรกะข้ามของซ้ำและการตั้งชื่อไฟล์เหมือนกันฟรี ๆ ไม่มีโค้ดสองทางให้ดูแล

### เติมทีละหลายใบ

ผลพลอยได้: อัป **ZIP ชุดเต็มทั้งก้อน** ซ้ำได้อย่างปลอดภัย ระบบจะเติมเฉพาะส่วนต่าง
และ ZIP แต่ละครั้งเก็บแยกไฟล์บน R2 (`bundle-<เวลา>.zip`) จึงย้อนดูต้นทางได้เสมอ

หลังเติมเสร็จ ถ้ารอบนั้นมีไฟล์ Excel อยู่แล้ว ระบบจะตั้งงานจับคู่ต่อให้อัตโนมัติ

## 7.2 การเผยแพร่ (Publishing)

เผยแพร่ **ทีละคน ไม่ใช่ทั้งรอบ** เพราะการนำเข้ารอบแรกมักมีของตกหล่นเสมอ
ถ้าต้องรอจนครบทุกคน ผู้ปกครองของคนที่ข้อมูลครบแล้วก็ต้องรอไปด้วยโดยไม่จำเป็น

### เงื่อนไขการค้างไว้

| เงื่อนไข | เหตุผล |
|---|---|
| มีใบ Perfect Score แต่ไม่มีใบเหรียญ | เป็นไปไม่ได้ตามกติกาการให้รางวัล = ไฟล์ใบเหรียญตกหล่น |

กันไว้ **ทั้งคน** ไม่ใช่กันเฉพาะใบนั้น เพราะสิ่งที่ผู้ปกครองควรได้คือใบเหรียญที่ยังมาไม่ถึง
ปล่อยใบ Perfect Score ออกไปก่อนจะทำให้เข้าใจผิดว่านั่นคือรางวัลที่ได้

### ตัวเลือกของรอบ: ฮ่องกงส่งฉบับจริงมาแบบไหน

Perfect Score เป็นรางวัลเสริมที่ให้คนได้เหรียญทองซึ่งทำคะแนนได้ดี
บางรอบฮ่องกงส่งฉบับจริงมาทั้งสองใบ บางรอบส่งมาแค่ใบเหรียญ

| ตัวเลือก | ผล |
|---|---|
| ทั้งสองใบ | เผยแพร่ทั้งใบเหรียญและใบ Perfect Score |
| เฉพาะใบเหรียญ | ซ่อนใบ Perfect Score ของคนที่มีทั้งสองใบ (ไม่ลบ) |

**ต้องเลือกก่อนถึงจะกดเผยแพร่ได้** และขึ้นเฉพาะรอบที่มีคนถือทั้งสองใบจริง
รอบที่ไม่มีใครได้ Perfect Score จะกดเผยแพร่ได้ตามปกติ

### ข้อบังคับเชิงโครงสร้าง

**สถานะเผยแพร่ถูกเขียนที่เดียวเท่านั้น** คือตอนกดปุ่มเผยแพร่ (`apps/web/src/lib/publish.ts`)
ตัวจับคู่ฝั่ง worker ห้ามตัดสินเอง ทำได้แค่รักษาค่าเดิมไว้ตอนสร้างเกียรติบัตรใหม่

เคยพลาดมาแล้ว: ตัวจับคู่เคยตั้งสถานะจาก `batch.status` ซึ่งตอนกำลังจับคู่จะเป็น `MATCHING` เสมอ
ผลคือ **ทุกครั้งที่จับคู่ใหม่ ทั้งรอบถูกยกเลิกเผยแพร่เงียบ ๆ** โดยไม่มีอะไรฟ้อง

## 8. สถานะการทำจริง (อัปเดตหลังตรวจไฟล์จริง)

ตรวจกับชุด **HKIMO Final 2026** (242 หน้า, 5 โฟลเดอร์รางวัล, Excel 240 แถว) ผลดังนี้:

| สิ่งที่ตรวจ | ผล |
|---|---|
| อ่านชื่อจากหน้าเกียรติบัตร | 242/242 |
| อ่าน `Cert No` | 242/242 |
| อ่านระดับชั้น | 242/242 และตรงกับ `GRADE` ใน Excel ทุกแถว |
| อ่านปี ค.ศ. และรอบ | 242/242 (Final Round 2026) |
| รางวัลบนหน้าตรงกับชื่อโฟลเดอร์ | 239/239 (อีก 3 หน้าคือ Perfect Score ซึ่งไม่มีบรรทัดรางวัล) |
| เลขบนหน้าหาเจอใน Excel | 242/242 และชื่อตรงกันทุกหน้า |

ตรวจซ้ำได้ด้วย `docker compose exec worker python scripts/check_real_files.py`

**ข้อสังเกตจากข้อมูลจริง:** ผู้ที่ได้ `PERFECT SCORER` 3 คน — 2 คนมีทั้งหน้า Gold และหน้า

ระบบจึงออกเกียรติบัตรตามจำนวนหน้าที่มีจริง ไม่ใช่ตามจำนวนแถวใน Excel
