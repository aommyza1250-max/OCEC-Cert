# ค่าใช้จ่ายและกำลังรองรับระบบ

ปรับปรุง 1 ตุลาคม 2569 ราคาต่อไปนี้อ้างอิง Railway container และ Cloudflare R2 Standard ไม่ใช่ VM/sandbox ของ Railway

## ข้อสรุปสำหรับวางงบ

แบบจำลองผู้ใช้ 10,000 คนต่อเดือนให้ต้นทุน **ประมาณ 205 บาท** ในสมมติฐานปกติ และ **ประมาณ 455 บาท** ในสมมติฐานเผื่อทรัพยากร แนะนำกันงบ **600 บาทต่อเดือน** สำหรับ production หนึ่งชุดบน Hobby หากต้องใช้ Pro ให้กันอย่างน้อย **1,000 บาทต่อเดือน** สำหรับกรณีนี้ จำนวนคนต่อเดือนไม่เท่ากับคนพร้อมกัน ต้องวัดโหลดช่วงพีคต่างหาก

เงินบาทใช้อัตรา **35 บาท/USD เพื่อวางแผน** ไม่ใช่ราคาตลาดที่ยืนยัน คำนวณก่อนภาษี ค่าบัตร โดเมน ทีมดูแล และ environment อื่น ต้องแทนค่าด้วย invoice และอัตราตัดบัตรจริง

| Railway egress | GB ออกจาก Railway ไป internet รวม worker อัป PDF/preview ไป R2 | $0.05/GB |
| Railway volume | GB-month ของพื้นที่ฐานข้อมูล | $0.15/GB-month |
| Railway build | CPU/RAM ในขั้น build | ไม่คิดค่า build ตามราคาปัจจุบัน |
| R2 Standard storage | GB-month ส่วนเกินโควต้า 10 | $0.015/GB-month |
| R2 Class A | เขียน/list ส่วนเกิน 1 ล้านครั้งต่อเดือน | $4.50/ล้าน |
| R2 Class B | อ่าน/head ส่วนเกิน 10 ล้านครั้งต่อเดือน | $0.36/ล้าน |
| R2 egress | ดาวน์โหลดไฟล์ออกสู่ internet | $0 |

Hobby $5 รวมเครดิต usage $5; จ่าย `max(5, Railway usage)` ไม่ใช่ $5 บวก usage ทั้งก้อน Pro ใช้ floor $20 ตามเครดิต $20 โดยไม่รวมส่วนลดชั่วคราว แพ็กเกจอื่น และรายการเพิ่ม

Cloudflare มีการปัดหน่วยคิดเงิน เช่น R2 operations เกินหน่วยล้านต้องปัดขึ้น ห้ามใช้สูตรเศษล้านอย่างเดียวเมื่อเกิดส่วนเกิน Free tier เป็นระดับบัญชี ไม่ได้ให้ใหม่ทุก bucket และ Workers Free จำกัดรายวัน ไม่ใช่รายเดือน

## สมมติฐานผู้ใช้

หนึ่งคนเข้า 1 session ต่อเดือน ค้น 3 ครั้ง ดู preview 4 รูป ดาวน์โหลด WebP 2 ใบ หน้าเว็บรวมต่อคน 0.5 MB จาก Railway สมมติ WebP เฉลี่ย 0.6 MB/ใบจาก R2 และ cache miss ทุกครั้งเพื่อเผื่อคำขอจริง ค่า 0.6 MB เป็นสมมติฐานวางแผน ต้องแทนด้วยค่าเฉลี่ยของรูป 150 DPI / quality 85 หลังย้ายข้อมูลจริง

| ผู้ใช้/เดือน | ค้น | อ่านไฟล์ R2 | ไฟล์ R2 ขาออก | เว็บขาออก Railway |
|---|---:|---:|---:|---:|
| 1,000 | 3,000 | 6,000 | 3.60 GB | 0.5 GB |
| 5,000 | 15,000 | 30,000 | 18.00 GB | 2.5 GB |
| 10,000 | 30,000 | 60,000 | 36.00 GB | 5.0 GB |

ไฟล์ออก R2 ไม่เสีย egress แต่คิดคำขอหากเกินโควต้า คำขอภาพที่เบราว์เซอร์อ่านหลายช่วงและ HEAD อาจมากกว่าจำนวนปุ่มดาวน์โหลด จึงเผื่อรวมเป็น 120,000 Class B/เดือน และ 100,000 Class A/เดือนจากงานนำเข้า ยังอยู่ใน free tier หากบัญชีไม่มีงานอื่นใช้ร่วม รูปเดียวต่อใบทำให้การเปิดภาพขยายจาก URL เดิมมักใช้ browser cache ได้ แต่ตารางด้านบนเผื่อว่าไม่ใช้ cache

## แบบจำลองปกติ

ใช้ 30 วัน 720 ชั่วโมง RAM รวมเฉลี่ย 0.43 GB CPU idle รวมเฉลี่ย 0.04 vCPU volume ฐานข้อมูล 1 GB หนึ่งค้นใช้ CPU รวม web+DB 0.15 วินาที งานนำเข้า 10 core-hours/เดือน worker อัปไฟล์ไป R2 รวม 0.4 GB ต่อเดือน R2 storage เฉลี่ย 12 GB-month (คิดส่วนเกิน 2 GB = $0.03)

ฐาน: `0.43×10 + 0.04×20 + 1×0.15 = $5.25`

เพิ่มค้น: `ผู้ใช้×3×0.15 / 3600 / 720 ×20`

เพิ่มนำเข้า: `10/720×20 = $0.2778`

egress: `(ผู้ใช้×0.0005 + 0.4)×0.05`

| ผู้ใช้/เดือน | Railway | R2 | รวม USD | บาทที่ 35/USD |
|---|---:|---:|---:|---:|
| 1,000 | 5.5763 | 0.03 | 5.6063 | 196.22 |
| 5,000 | 5.6901 | 0.03 | 5.7201 | 200.20 |
| 10,000 | 5.8325 | 0.03 | 5.8625 | 205.19 |

ทั้งหมดเป็น **สมมติฐานวางแผน** ไม่ใช่ผลวัด RAM/CPU ล่าสุด ค่า CPU นำเข้าต่างมากตามแบบ PDF จำนวนหน้าและรอบที่มีต่างชาติ ต้องปรับจาก metrics

## แบบจำลองเผื่อ 10,000 คน

RAM รวมเฉลี่ย 0.8 GB, CPU รวมเฉลี่ย 0.12 vCPU (รวมค้นแล้ว), DB volume 5 GB, egress Railway 20 GB, งานนำเข้าเพิ่ม 20 core-hours, R2 30 GB-month, คำขอใน free tier, preview ไม่เกินเพดานรายวัน

`Railway = 0.8×10 + 0.12×20 + 5×0.15 + 20×0.05 + 20/720×20 = $12.7056`

`R2 = (30−10)×0.015 = $0.30`

รวม `$13.0056 × 35 = 455.19 บาท` กันส่วนเผื่อ 20% เป็น 546.23 บาท จึงปัดงบเป็น **600 บาท/เดือน** หากเปลี่ยนเป็น Pro และ usage ยังต่ำกว่า floor: `$20.30×35×1.2 = 852.60 บาท` จึงกัน **1,000 บาท/เดือน**

## สิ่งที่ทำให้งบเพิ่ม

- RAM เพิ่ม 0.1 GB เปิดเต็มเดือน เพิ่ม $1 ≈35 บาท แม้ไม่มีคนเข้า
- CPU ใช้ 1 core-hour เพิ่ม $0.0278 ≈0.97 บาท (เดือน 720 ชั่วโมง)
- Railway egress เพิ่ม 10 GB เพิ่ม $0.50 ≈17.50 บาท worker ส่งไฟล์ไป R2 เป็น egress ด้วย
- R2 เก็บเพิ่ม 100 GB-month หลังโควต้าฟรี เพิ่ม $1.50 ≈52.50 บาท; หากเก็บ Standard ไม่เกิน 10 GB-month และคำขอไม่เกินโควต้าฟรี ค่า R2 เป็นศูนย์
- เก็บ ZIP หลายร้อย MB ต่อรอบ ทำให้พื้นที่ขึ้นเร็ว ระบบล้างเมื่อครบเงื่อนไข ไม่ใช่เมื่ออัปเสร็จทันที
- Staging ใช้ RAM/CPU/volume แยก แม้อาจแชร์ plan floor ภายใน workspace เดียวกัน ต้องรวม usage ทั้ง workspace
- Workers Free อาจเกิน 100,000 requests ในวันประกาศแม้คนรวมต่อเดือนต่ำ หากอัปเป็น Paid มี minimum $5 แยกจาก Railway และคิดส่วนเกินตามแพ็กเกจ
- เปิด replica เพิ่มทำให้ memory และตัวนับ rate limit เปลี่ยน ต้องย้าย rate limit ไปส่วนกลางก่อน

## กำลังรองรับและตรวจบิล

10,000 คนกระจาย 30 วัน ≈333 คน/วัน และ 1,000 search/วัน แต่ถ้าทั้งหมดเข้าใน 10 นาทีจะมี 30,000 search/600s = 50 search/s ยังไม่รวม request เว็บและดาวน์โหลด จึงห้ามรับรองการไม่ล่มจากยอดรายเดือน

ข้อมูลทดสอบโหลดเก่าไม่ใช่หลักฐานรับรองรุ่นปัจจุบัน ให้ทดสอบ staging ด้วย scripts/loadtest.js และเกณฑ์ p95 <500ms error<1% ก่อนวันประกาศ ดู CPU RAM queue และ DB พร้อมกัน ห้ามยิง load test ใส่ production โดยไม่มีแผน

ตรวจ Railway Usage ตามรอบ billing และ Cloudflare R2 Metrics / Workers Metrics ทุกเดือน เปรียบเทียบกับสมมติฐาน ตรวจค่าเครดิตชั่วคราวแยกจากต้นทุนปกติ และตั้งงบแจ้งเตือนโดยเจ้าของบัญชี
