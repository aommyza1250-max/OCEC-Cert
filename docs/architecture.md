## ทำไมคิวงานอยู่บน Postgres ไม่ใช่ Redis

งานนำเข้าเกิดวันละไม่กี่ครั้งตอนแอดมินอัปโหลดไฟล์ ไม่คุ้มกับค่า service เพิ่มบน Railway
`SELECT ... FOR UPDATE SKIP LOCKED` ให้ความสามารถที่จำเป็นครบแล้ว:
ล็อกงานไม่ให้ซ้ำ, ทนการรีสตาร์ท, และขยายเป็นหลาย worker ได้ถ้าวันหนึ่งต้องการ

## ทำไมรางวัลต้องมาจากชื่อโฟลเดอร์

แอดมินอัปโหลด ZIP ที่แยกโฟลเดอร์ตามรางวัล (`gold/`, `silver/`, `bronze/`, `merit/`, `perfect score/`)
ระบบอ่านรางวัลจากชื่อโฟลเดอร์ ไม่ใช่จากข้อความบนหน้า เพราะ**หน้า Perfect Score
ไม่มีข้อความรางวัลพิมพ์อยู่เลย** ชื่อโฟลเดอร์จึงเป็นแหล่งเดียวที่รู้รางวัลได้ครบทุกใบ

เจอโฟลเดอร์ที่แปลงเป็นรางวัลไม่ได้ ระบบจะ**หยุดทั้งงานพร้อมบอกว่าเจอชื่ออะไร**
ไม่ใช่เดาหรือข้าม เพราะรางวัลผิดจะไปโผล่บนหน้าเว็บของเด็ก

## ไฟล์ใหญ่ไม่ผ่านหน่วยความจำ

ZIP จริงที่ทดสอบมีขนาด 359 MB (PDF ข้างในรวม 385 MB) worker จึง:
1. ดาวน์โหลดจาก R2 **ลงดิสก์** ไม่ใช่เข้าหน่วยความจำ
2. อ่าน PDF ออกมาจาก ZIP **ทีละไฟล์**

ผลคือใช้หน่วยความจำประมาณ 330 MB แทนที่จะเป็น 750 MB+ ซึ่งจะทำให้ถูกฆ่าบน Railway

## ทำไมต้องมีตาราง staging_pages

เพราะตอนตัด PDF ยังไม่รู้ว่าหน้าไหนเป็นของใคร รู้แค่ชื่อที่อ่านได้จากหน้ากระดาษ
การแยกขั้น "ตัด" กับ "จับคู่" ออกจากกันทำให้:

- จับคู่ใหม่ได้โดยไม่ต้องตัด PDF ใหม่ (Excel ผิดรอบแรกก็อัปใหม่ได้เลย)
- มีที่เก็บหน้าที่จับคู่ไม่ได้ ให้แอดมินตามเก็บทีหลัง
- ตรวจยอดได้ว่าหน้าในไฟล์กับรายชื่อใน Excel ตรงกันไหม

## การเผยแพร่เป็นขั้นตอนแยก

`certificates.published_at` เป็น null จนกว่าแอดมินจะกดเผยแพร่
ตั้งใจบังคับให้มีคนตรวจก่อนเสมอ เพราะถ้าจับคู่ผิดแล้วเผยแพร่ทันที
ผู้ปกครองจะดาวน์โหลดเกียรติบัตรของเด็กคนอื่นไปได้ ซึ่งแก้ย้อนหลังไม่ได้
